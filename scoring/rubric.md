# nlpm-qwen 评分标准（100 分制）

> 评分公式：`最终分数 = max(0, min(100, 100 + 所有扣分之和))`
> 扣分都是负数。底线是 0，上限是 100。没有加分——默认假设工件是良好的，质量由缺失或错误的部分来衡量。

---

## 评分等级

| 分数段 | 等级 | 含义 |
|--------|------|------|
| 90-100 | 优秀 | 生产就绪，只有微小或没有问题 |
| 80-89 | 良好 | 扎实，有一两个非关键缺陷 |
| 70-79 | 及格 | 达到阈值，但有明显需要改进的地方 |
| 60-69 | 弱 | 低于阈值，有重大发现 |
| <60 | 重写 | 根本性问题，建议从头重写 |

**默认通过阈值**：70 分。可在项目配置中调整。

**中文模糊量化词同样适用**：
"尽量"、"适当"、"相关"、"合适"、"尽可能"、"某种程度上"、"一般来说"等，没有具体标准时同样扣分。

## 校准示例

### 优秀智能体（97 分）

```yaml
---
name: security-reviewer
description: |
  审计认证变更的安全漏洞。不用于一般风格审查；使用 code-reviewer。
  <example>
  Context: 开发者在 PR 前重构认证模块
  user: "检查认证变更有没有安全漏洞"
  assistant: "我会调度 security-reviewer 审计认证变更的漏洞。"
  </example>
model: sonnet
tools: [Read, Grep, Glob]
---

## 使命
分析源代码文件中的安全漏洞、认证问题和会话管理缺陷。
生成带有严重程度标记的结构化报告。

## 指令
1. 使用 Glob 发现匹配目标模式的文件
2. 使用 Read 检查每个文件
3. 使用 Grep 交叉引用导入和使用模式
4. 对每个发现，分类严重程度并提供具体修复
5. 生成输出报告

## 边界
- 不要修改任何文件（只读分析）
- 不要运行 shell 命令
- 不要报告风格问题（交给 linter）
- 如果没有指定目标模式，分析 src/ 中的所有文件

## 输出格式

对于每个发现：

**[严重程度] 发现标题**
- 文件：`path/to/file`
- 行号：{N}
- 发现：{描述}
- 修复：{具体修复}

严重程度：CRITICAL > HIGH > MEDIUM > LOW > INFO

最后一行：
- `PASS: 没有问题`
- `WARN: 发现 {N} 个警告`
- `FAIL: 发现 {N} 个错误`

## 错误处理
- 如果没有文件匹配模式：报告 "No matching files for pattern: {X}"
- 如果文件无法读取：跳过并在报告中注明
```

**扣分**：
- R01：1 个模糊量化词（"所有"没有具体说明）(-2)
- R12：输出格式可以更具体（缺少 JSON schema）(-1)

**总分**：100 - 2 - 1 = 97

## 评分流程

1. **识别工件类型**：根据路径和 frontmatter 判断是 Skill、Agent、Command、Rule 还是项目文档
2. **加载对应评分表**：应用该类型的扣分项
3. **检查模糊量化词**：扫描所有工件类型的通用扣分
4. **计算总分**：100 + 所有扣分之和
5. **确定等级**：根据分数段确定等级
6. **生成报告**：列出每个扣分项、规则编号、具体位置

---

## 重要提醒

**分数只是参考，实际效果才是目标。**

一个 90 分的智能体如果实际使用中触发不准确、输出不稳定，那它就不是好智能体。
一个 70 分的智能体如果实际使用中表现良好，那它就是合格的。

评分的目的是帮你发现问题，不是让你追求高分。
